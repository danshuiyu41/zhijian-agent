## 三、协作机制

### 1. 每周固定节奏

| 时间 | 内容 |
|---|---|
| 周一晚 | 对齐本周目标，拆任务、定验收标准 |
| 周三晚 | 中期检查，跑一次自检脚本，暴露问题 |
| 周日晚 | 复盘 + 更新文档，把结论沉淀进仓库 |

### 2. 用工具保证协作不乱

- **版本控制**：全部代码托管在 Git 仓库，两人各自分支开发，合并前必须通过
  `python check_all.py` 的 9 项自检，避免"能跑但不达标"的代码进主干。
- **单一事实来源**：所有指标只在 `runs/metrics.json` 里取，文档里不手写数字，
  防止出现"文档说 99%、代码跑出 96%"这类对不上的情况。
- **自动检查拦截低级错误**：我们写了 9 个自检脚本，专门拦截各自踩过的坑——

  | 脚本 | 拦截的问题 |
  |---|---|
  | `check_syntax.py` | 全角引号写在 Python 字符串里导致语法错误 |
  | `check_frontend.py` | 前端调用了后端不存在的接口 |
  | `check_vars.py` | CSS 变量重命名后 JS 里残留旧变量名，导致图表变灰 |
  | `check_css.py` | 样式选择器与实际 class 不匹配 |
  | `check_contrast.py` | 文字与背景对比度不足，肉眼难读 |
  | `check_overflow.py` | 页面元素溢出、横向滚动条 |
  | `check_served.py` | 服务实际返回的页面与源文件不一致（改错文件） |
  | `selfcheck_model.py` | 权重与类别数与配置不符 |
  | `bench_speed.py` | 性能退化（推理耗时突然变慢） |

### 3. 关键决策一起定，实现分头做

三个真正有争议的点，都是两人各自拿方案 + 实测数据，再一起拍板：

1. **模型选哪个**——最初想上 ResNet18，实测后 MobileNetV3-Small 精度持平、
   参数量只有 1/11（1.077 M vs 11.2 M），CPU 推理快 3 倍以上，遂改选小模型。
2. **严重度怎么算**——第一版把"风险等级"直接当分数加，结果输出只有 A 和 D
   两档，中间没有过渡，不可用。改成嵌套加权（风险做先验、置信度与面积做修正）
   后，A–E 五档分布合理。
3. **热力图要不要默认开**——Grad-CAM 占了整条链路 90% 的耗时（1905 ms）。
   我们没有直接砍掉功能，而是改成异步按需取图，界面耗时从 2598 ms 降到 296 ms，
   功能一个没少。
